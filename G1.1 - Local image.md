# G1.1 - Local image

> Estado: **investigación específica cerrada; listo para implementación**. No se modificó código de producto durante esta investigación. Se prototipó la vertical completa en una copia temporal de HEAD y luego se eliminó.

## Objetivo

Agregar una única tool pública:

`filesystem_view_image(path, workId?)`

Debe permitir que el agente vea directamente una imagen local conocida sin:

- abrir una GUI;
- leerla como texto;
- ejecutar shell/base64 manual;
- depender de Computer;
- decodificar o recodificar localmente la imagen.

G1.1 agrega **1 tool pública**:

- sin Work Plan: 17 -> **18**;
- Host normal con Work Plan: 19 -> **20**.

## Formatos G1.1

Soportar:

- PNG -> `image/png`;
- JPEG/JPG/JFIF/Exif codificado como JPEG -> `image/jpeg`;
- WebP -> `image/webp`.

OpenAI acepta actualmente PNG, JPEG y WebP como formatos de entrada visual. También acepta GIF no animado, pero GIF queda fuera de G1.1 para mantener la primera superficie pequeña y evitar agregar lógica específica de frame/animación.

La extensión **no es autoritativa**. El formato se detecta por contenido:

- un PNG llamado `image.bin` sigue siendo PNG;
- un archivo `.png` que no contiene una estructura PNG válida se rechaza.

## Resolver de paths compartido

Hallazgo actual:

`FilesystemCapability.ResolvePath` es privado y contiene exactamente la semántica que Visual Files necesita:

- absoluto -> `Path.GetFullPath`;
- relativo -> requiere WorkSession;
- relativo -> se resuelve contra `WorkSession.BaseDirectory`;
- path inválido -> `invalid_argument`.

No copiar esa lógica.

G1.1 debe extraerla a:

`FilesystemPathResolver`

interno en Core/Filesystem y hacer que **FilesystemCapability y VisualFilesCapability usen el mismo resolver**.

El prototipo compiló correctamente con esta extracción y conservó el comportamiento existente.

## Lectura estable del archivo

La idea inicial de G era comparar `length + lastWriteTimeUtc` antes/después. La investigación G1.1 cambia esa decisión.

Microsoft documenta que `LastWriteTimeUtc` puede ser inexacto o actualizarse con retraso. No debe usarse como garantía fuerte de estabilidad.

### Decisión

Abrir con:

```text
FileMode.Open
FileAccess.Read
FileShare.Read
FileOptions.Asynchronous | FileOptions.SequentialScan
```

Mientras Loom mantiene ese handle:

- otros lectores pueden abrir el archivo;
- nuevas aperturas de escritura no están permitidas;
- delete/rename no están compartidos;
- si ya existe un writer incompatible, el open falla con sharing violation.

Como la imagen máxima es 6 MiB, el lock dura sólo la lectura acotada.

Si hay sharing/lock violation:

```text
code = busy
retryable = true
details.reason = file_busy
```

El prototipo validó este comportamiento: con un writer abierto la tool devolvió `busy/file_busy`; al cerrar el writer leyó normalmente.

Esto elimina la necesidad de `file_changed_during_read` en G1.1.

## Algoritmo de lectura

1. resolver path compartido;
2. verificar que existe como archivo;
3. abrir con `FileShare.Read`;
4. leer `stream.Length`;
5. si >6 MiB, cerrar y devolver `unsupported/image_too_large`;
6. reservar exactamente ese tamaño;
7. `ReadExactlyAsync(..., cancellationToken)`;
8. validar contenedor/formato sin decodificar;
9. devolver bytes originales sin cambios;
10. MCP calcula presupuesto serializado 9 MiB;
11. sólo entonces crea el `ImageContentBlock`.

No hay estado durable, handles nuevos ni ResourceRegistry.

## Validación de formato

G1.1 no debe incorporar un decoder completo ni una nueva dependencia.

La validación es de **estructura/contenedor suficiente para descartar archivos falsos o truncados obvios**, no una prueba completa de conformance del bitstream.

### PNG

Validar:

- firma de 8 bytes;
- chunks dentro de bounds;
- primer chunk = `IHDR`;
- largo IHDR = 13;
- width/height != 0;
- `IEND` de largo 0 como último chunk.

No validar CRC ni inflar IDAT.

### JPEG

Validar:

- SOI al comienzo;
- EOI al final;
- estructura de marker segments previa al scan;
- longitudes de segmentos dentro de bounds;
- al menos un SOF válido;
- al menos un SOS posterior al SOF.

No decodificar entropy-coded data.

El prototipo aceptó JPEG baseline y progressive reales.

### WebP

Validar:

- `RIFF`;
- declared RIFF size coincide con el archivo;
- FourCC `WEBP`;
- primer chunk = `VP8 `, `VP8L` o `VP8X`;
- cada chunk respeta su tamaño/padding y permanece dentro del archivo.

El prototipo aceptó:

- WebP lossy;
- WebP lossless;
- WebP extended con alpha.

No rechazar WebP animado específicamente en G1.1: el formato WebP lo permite y OpenAI documenta WebP como input compatible sin distinguirlo. Si el cliente/modelo impone una limitación adicional, debe descubrirse en la validación real por tunnel.

## Por qué no usar decoder local

No usar en G1.1:

- System.Drawing;
- ImageSharp;
- WIC/BitmapDecoder;
- Pillow;
- codecs opcionales del sistema.

Razones:

- Loom no necesita interpretar píxeles; el modelo ya tiene visión;
- evita nueva dependencia y superficie de parser/decoder;
- evita que soporte WebP dependa de codecs instalados localmente;
- bytes se conservan exactamente;
- el límite de 6 MiB hace la lectura local acotada.

El cliente/modelo sigue siendo la autoridad final sobre si un bitstream profundamente corrupto puede decodificarse.

## Tool MCP

DTO estructurado:

```text
VisualImageDto
- requestedPath
- fullPath
- mimeType
- sizeBytes
```

Content exitoso:

```text
TextContentBlock breve
ImageContentBlock.FromBytes(bytes, mimeType)
```

Annotations:

```text
ReadOnly = true
Destructive = false
Idempotent = true
OpenWorld = false
```

Descripción debe explicar:

- una imagen por llamada;
- PNG/JPEG/WebP;
- absoluto o relativo a WorkSession;
- devuelve bytes sin resize/conversión/OCR;
- usarla para inspección visual, no `filesystem_read_files` ni shell/base64.

Agregar también una frase breve a ServerInstructions para favorecer esta ruta cuando la imagen local ya es conocida.

## Guard MCP

Reutilizar G1.0:

```text
MaxImageBytes = 6 MiB
MaxVisualCallToolResultBytes = 9 MiB
```

Orden:

1. Windows provider corta >6 MiB antes de reservar;
2. adapter arma sólo metadata estructurada;
3. `McpVisualPayloadLimits.IsWithinLimits(...)`;
4. si excede 9 MiB:
   - no crear/enviar image content;
   - `unsupported`;
   - `details.reason = visual_payload_too_large`;
5. si entra, usar `ImageContentBlock.FromBytes`.

Esto conserva ~1 MiB de margen respecto del hard limit de 10 MiB del Secure MCP Tunnel.

## Errores G1.1

| Caso | code | details.reason |
|---|---|---|
| relativo sin WorkSession / path inválido | `invalid_argument` | - |
| archivo inexistente | `not_found` | - |
| acceso ACL | `access_denied` | - |
| writer/lock activo | `busy` | `file_busy` |
| formato no soportado o estructura claramente inválida | `unsupported` | `unsupported_image_format` |
| binario >6 MiB | `unsupported` | `image_too_large` |
| resultado MCP >9 MiB | `unsupported` | `visual_payload_too_large` |
| otro I/O | `execution_failed` | - |
| cancelación | semántica InvocationRunner existente | - |

No agregar top-level error codes nuevos.

## Acceptance real por Secure MCP Tunnel

Esto **no se ejecutó durante investigación** para no modificar el runtime instalado ni volver a forzar el túnel.

Es requisito de cierre de implementación G1.1:

1. build/package de la versión nueva;
2. actualización controlada del runtime portable local con rollback disponible;
3. comprobar que ChatGPT descubre `filesystem_view_image`;
4. llamar la tool sobre una imagen visualmente inequívoca;
5. confirmar que el modelo realmente ve y describe el contenido, no sólo metadata;
6. probar PNG, y al menos una llamada JPEG o WebP;
7. no hacer stress del límite de 10 MiB por tunnel: los caps ya están cubiertos localmente.

Fresh-agent exhaustivo queda para G1.4; G1.1 sólo necesita smoke real del nuevo tipo de contenido.

- assets runtime;

Por tanto no cambia el formato portable. Aun así, como se necesita instalar el Host nuevo para la prueba real por tunnel, conviene ejecutar el builder portable y sus integration tests durante implementación.

## Conclusión

G1.1 puede implementarse como una vertical pequeña y aislada.

No quedan decisiones arquitectónicas bloqueantes.

La diferencia principal frente al diseño preliminar de G es:

- **antes:** lectura con FileShare.ReadWrite/Delete + comparación de metadata;
- **ahora:** lectura estable con FileShare.Read y error retryable `busy/file_busy` si existe un writer.

Esto da una garantía más fuerte y elimina dependencia de timestamps de filesystem.
