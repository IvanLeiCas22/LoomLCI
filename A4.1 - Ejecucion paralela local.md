# A4.1 — Ejecución paralela local con loom.process.run_many

> 2026-10-08. **Implementado y validado en el código fuente / Host Release aislado**. **No instalado** en la Release 5 productiva ni en el túnel HTTP experimental. Requiere un despliegue posterior aprobado. ChatGPT normal conserva 25 tools públicas MCP; el bridge Python pasa de 15 a 16 capabilities.

## Motivación

A3.3 mostró que operaciones `filesystem_read_files` pueden llegar en paralelo desde ChatGPT normal, pero varias `process_run` potencialmente modificadoras llegan a menudo escalonadas. El Host sí admite procesos simultáneos. Agrupar trabajo en un solo `python_execute` evita múltiples viajes MCP, sin subagentes ni cuota adicional de inferencia.

La API privada `loom.process.run_many` se implementa en `src/LoomLCI.Core/Python/PythonProcessBridgeModule.cs` y `runtime/python/loom_bridge.py`. No agrega tools MCP ni cambia metadatos públicos.

## Ejemplo

```python
import loom.process

batch = loom.process.run_many(
    [
        {"id": "unit", "executable": "dotnet.exe",
         "arguments": ["test", "LoomLCI.slnx", "--no-restore"]},
        {"id": "git", "executable": "git.exe",
         "arguments": ["status", "--short"]},
    ],
    max_concurrent=2,
    job_timeout_seconds=30,
    batch_timeout_seconds=45,
    max_output_chars=4096,
)
for item in batch["jobs"]:
    print(item["id"], item["outcome"], item["exit_code"])
```

Usar un `timeoutSeconds` externo de `python_execute` **superior a `batch_timeout_seconds`**, contando provisionamiento y transporte. Si el lote vence antes, retorna `timed_out=true` y clasifica trabajos pendientes/no iniciados. Ante cancelación externa, propaga cancelación después de esperar limpieza y no promete entregar resultados parciales.

## Contrato

- `jobs`: lista de 1–32 objetos con `id` único (1–64 caracteres), `executable` no vacío, y opcionalmente `arguments`, `working_directory` y `environment`. Las rutas y permisos siguen el Full Trust habitual; no se incorpora sandbox artificial.
- `max_concurrent`: 1–8 (por defecto 4). Semáforo en el Host y resultados en orden de entrada.
- `job_timeout_seconds`: 1–600 (por defecto 30); `batch_timeout_seconds`: 1–540 (por defecto 45).
- `max_output_chars`: 1–65.536 por proceso (por defecto 4096), compartidos entre stdout y stderr, con flags de truncamiento y contadores observados.
- Retorno: `{"jobs":[...], "timed_out":bool}`. Cada resultado: `id`, `outcome`, `exit_code`, `process_id`, `started_at`, `exited_at`, `stdout`, `stderr`, `stdout_truncated`, `stderr_truncated`, `stdout_observed_chars`, `stderr_observed_chars`, `error_code`, `error_message`. Los campos no disponibles quedan null; salidas vacías cuando no se ejecutó.
- `outcome`: `success`, `nonzero_exit`, `timeout`, `launch_error` o `not_started`. Un código de salida distinto de cero **no** es fallo del bridge. Errores de validación de toda la solicitud emiten `LoomError(invalid_argument)` antes de iniciar procesos.
- Los trabajos utilizan `ProcessCapability.RunAsync`, que espera tanto salida como finalización de los pumps y dispone cada proceso vía `await using`. No crea handles persistentes. Su cancelación está ligada al worker, al lote y a su timeout individual.
- El scheduler usa `Task.WhenAll` y semáforo; en cancelación externa espera las disposiciones de todas las tareas activas antes de propagarla. No reintentar ciegamente tras timeout remoto si se desconoce qué se ejecutó.

## Validación

- Compilación Release Core: 0 advertencias y 0 errores.
- Tests unitarios: límites inválidos (incluidos 0/33 jobs, concurrencia 0/9, tiempo/salida), IDs duplicados, claves desconocidas, orden, salidas, no-cero, fallos de inicio, cancelación individual/global, limpieza, y concurrencia máxima medida con provider fake.
- Integración MCP STDIO de Host Release: `loom.capabilities()` = **16**, tool catálogo = **25** (metadata pública sin cambios), invocación `run_many` comprobada con 3 comandos reales incluyendo uno exit 9.
- Suite completa Release, usando `LOOMLCI_TEST_HOST_DLL` para apuntar al Host Release: **379/379 PASS** (medición final con timeout individual incluido y Host Release explícito mediante la variable de entorno).
- Smoke separado de cancelación en Windows real: dos procesos PowerShell escribieron sus PIDs en un directorio temporal; `python_execute(timeoutSeconds=4)` interrumpió `run_many` y devolvió error de deadline; **2/2 procesos dejaron de existir**, WorkSession cerrada y Host aislado terminó con código 0. No quedaron archivos temporales.
- WorkSession/Host productivos no modificados.

## No incluido

No se implementó `start_many`, lotes duraderos, persistencia tras cierre de WorkSession, autoscheduler, workers de IA ni nuevos modelos. Este lote es **one-shot** y se consulta en una llamada; una fase posterior puede diseñar lifecycle persistente en el Host. Conservar la integración STDIO productiva hasta desplegar y hacer smoke final de fresh-agent.
