## Incidente de cutover y causa probable

Primer `update apply`: se inició a través del complemento experimental `LoomLCITestHTTP`. Aunque sus procesos se habían creado como `Independent` respecto de la WorkSession, **el Host HTTP y su tunnel-client habían sido lanzados desde LoomLCI productivo**. Al detener el runtime productivo, ambos túneles dejaron de responder y también desapareció el proceso actualizador. El Launcher quedó en Release 5 pero `stopped`, sin journal pendiente. Se recuperó con IvanSpace mediante `LoomLCI.Launcher.exe start`; quedó `healthy=true`, `ready=true`.

Hipótesis consistente con el código actual: Windows Job Objects anidados; `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` puede terminar descendientes incluso cuando se usan handles `Independent` a nivel de WorkSession. **Independent no garantiza independencia respecto de un Job Object antecesor.** No es evidencia de paquete corrupto ni una regresión de A4.1. Evitar en futuros cutovers procesos de supervisión lanzados desde el propio runtime a detener.

Segundo `update apply`: se ejecutó **directamente desde IvanSpace**, fuera del árbol de procesos de LoomLCI. Resultado: `exitCode=0`, `Update aplicado: 0.1.0-dev-6b1566a (sequence 6)`, rollback a Release 5 confirmado.

## Mejora operacional futura

No volver a utilizar un proceso auxiliar lanzado desde LoomLCI productivo como canal de supervisión durante su propio `stop/update/rollback`. Para cutovers, usar IvanSpace o un proceso iniciado explícitamente fuera de sus Jobs.
