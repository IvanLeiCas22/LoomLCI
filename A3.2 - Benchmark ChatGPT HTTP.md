# A3.2 — Benchmark real ChatGPT normal ↔ Streamable HTTP

> Fecha: 2026-10-08. **Conexión E2E HTTP confirmada; mejora de concurrencia E2E NO observada.** Sin cutover de producción.

## Entorno y método

- Complemento ChatGPT `LoomLCITestHTTP`, conectado al segundo túnel real `LoomLCI HTTP Test` por `tunnel-client` 0.0.14.
- Host experimental Streamable HTTP local, Stateless, con Bearer privado y ACL de Windows; instalación productiva STDIO separada e intacta.
- Orquestación mediante `functions.exec`: tres llamadas `mcp__LoomLCITestHTTP__process_run` con `Promise.all`, comparadas con tres `await` secuenciales. Cada operación: `powershell.exe -NoProfile -NonInteractive -Command "Start-Sleep -Milliseconds 1600; Write-Output A32_HTTP_OK"`.
- Las mediciones incluyen latencia del recorrido completo del chat y del túnel; un solo intento por modalidad, no benchmark estadístico.

## Resultados

| Ruta | Tiempo pared 3 solicitudes | Validación |
| --- | ---: | --- |
| HTTP desde ChatGPT, secuencial | **12,403 s** | 3/3 salida 0, `A32_HTTP_OK` |
| HTTP desde ChatGPT, `Promise.all` | **13,017 s** | 3/3 salida 0, `A32_HTTP_OK` |
| STDIO desde ChatGPT, A2, `Promise.all` | **11,23 s** | 3/3 salida 0 |
| HTTP directo local (A3.1), `Promise.all` | **1,867 s** | 3/3 salida 0 |

En HTTP remoto concurrente, los tiempos de inicio del Host fueron escalonados (~5,43 s y ~3,76 s de separación). La latencia de extremo a extremo no mejoró.

Prueba adicional: enviar en paralelo una lectura de `global.json` y un `process_run` de 1,6 s: **ambas llamadas terminaron después de ~4,97 s**; la lectura breve no obtuvo una respuesta temprana.

## Verificaciones de funcionalidad

- Catálogo ChatGPT: **25 herramientas expuestas** mediante el complemento HTTP.
- `work_create`: PASS. `filesystem_read_files` sobre `global.json`: PASS. `work_plan_get`: PASS. `work_close`: PASS.
- Se invocó también una llamada `python_execute` que concluyó en 3,82 s de ida/vuelta, pero su payload no quedó capturado por el script de orquestación que imprimió el resultado; **no usarla como validación de salida/correctitud del subtrabajo**.
- La WorkSession remota fue cerrada.

## Interpretación

- El Host HTTP **sí** ejecuta peticiones concurrentes cuando llegan directamente (A3.1).
- ChatGPT reconoce y usa el túnel HTTP **desde una conversación normal**.
- La ruta remota ChatGPT + Secure MCP Tunnel HTTP **continúa escalonando o demorando** llamadas enviadas conjuntamente; falta aislar si ocurre en la capa ChatGPT/orquestador, control-plane/poller o tunnel-client HTTP.
- No atribuir el bloqueo exclusivamente a STDIO ni afirmar que el simple cambio a HTTP resuelve concurrencia.
- No justificar una migración del Launcher a HTTP por mejora de rendimiento sin un hallazgo nuevo.

## Siguiente investigación propuesta

1. Evaluar observabilidad no sensible de tiempos: emisión desde cliente, recepción del poller, despacho al Host, finalización y entrega a ChatGPT; sin loggear credenciales ni payload de trabajo.
2. Probar el mismo patrón con una llamada `python_execute` que agrupe procesos locales; esta vía ya demostró paralelismo en A1/A2.
3. Con los resultados, decidir si la mejora corresponde al adaptador de herramientas, al túnel o sólo a ergonomía local.
4. Mantener STDIO instalado y HTTP experimental separado. **Nota histórica:** los procesos iniciales no permanecieron vivos durante el posterior cutover de Release 6; el entorno experimental se recuperó desde IvanSpace.

## Seguimiento A3.3 y resolución práctica (2026-10-08)

A3.3 investigó por qué el paralelo remoto de `process_run` no mejoraba. Los ensayos confirmaron que **la serialización no es global al túnel**:

- Tres llamadas `filesystem_read_files` por HTTP: **1,09 s concurrentes** frente a **3,10 s secuenciales**.
- Tres lecturas concurrentes por STDIO productivo: **1,24 s**.
- Tres `process_run` de `git --version` por HTTP concurrentes: **5,77 s**; la ejecución local de cada proceso duró sólo decenas de milisegundos.
- En una toma de 113 muestras de métricas del cliente HTTP, no se observaron más de un worker ocupado a la vez durante el patrón de procesos. Esto es **observación**, no prueba de que el cliente sólo admita uno.
- `filesystem_read_files` está anotado `ReadOnly=true, Destructive=false`; `process_run` está anotado `ReadOnly=false, Destructive=true`. Es **hipótesis**, no confirmación del comportamiento interno del servicio, que las llamadas potencialmente modificadoras reciban un tratamiento distinto. No alterar esas anotaciones para intentar acelerar ejecuciones.

Decisión: mantener **STDIO productivo**, no migrar a HTTP por rendimiento; aprovechar paralelismo local mediante el bridge `loom.process.run_many`. Esta capacidad se implementó, probó y desplegó en **Release 6** `0.1.0-dev-6b1566a`, con 25 herramientas públicas y 16 capacidades Python. El smoke fresh-agent concluyó `A41_FRESH_AGENT_OK`. Ver [[A4.1 - Ejecucion paralela local]] y [[A4.1 - Release 6 desplegada]].

**Lección de despliegue:** los procesos HTTP originales se habían lanzado desde un Host que se detuvo; ownership `Independent` en una WorkSession no evita necesariamente terminación por Windows Job Objects de procesos antecesores. Para futuros cutovers de LoomLCI, utilizar **IvanSpace u otro canal iniciado fuera del árbol productivo**. Los servicios HTTP experimentales se iniciaron nuevamente desde IvanSpace después de la Release 6, sin instalarse como servicios permanentes.
