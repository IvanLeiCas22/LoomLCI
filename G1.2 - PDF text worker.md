# G1.2 - PDF text worker

> Estado: **implementado en `b6e41fd`; validación local/STDIO/Host publicado/portable, cutover y smoke directo desde ChatGPT completados.** El runtime final está healthy/ready y `filesystem_read_pdf` fue invocada correctamente desde un chat con catálogo actualizado a 21 tools.

## Objetivo

Agregar una única tool pública:

`filesystem_read_pdf(path, workId?, startPage=1, maxPages=10)`

Debe extraer texto de PDFs locales de forma paginada y acotada, sin OCR ni render automático, manteniendo el parser PDF fuera del proceso principal de LoomLCI.

G1.2 agrega **1 tool pública**:

- sin Work Plan: 18 -> **19**;
- Host normal con Work Plan: 20 -> **21**.

## Parser

Mantener **PdfPig 0.1.16**.

A fecha 2026-10-05:

- 0.1.16 sigue siendo la última versión estable;
- 0.1.17 existe sólo como prerelease alpha;
- `dotnet list package --vulnerable --include-transitive` sobre un proyecto temporal con 0.1.16 no reportó vulnerabilidades conocidas;
- `dotnet list package --outdated` no encontró una actualización estable.

Para texto usar:

`ContentOrderTextExtractor.GetText(page)`

PdfPig recomienda este extractor frente a `page.Text` para texto destinado a indexación/RAG/LLMs.

## El aislamiento sigue siendo obligatorio

La decisión previa se mantiene.

PdfPig ha tenido y sigue teniendo clases de fallos donde PDFs malformados pueden provocar `StackOverflowException` u otros crashes no recuperables de forma segura dentro del Host. El corpus y fuzzing upstream confirman que un parser PDF no debe compartir proceso con LoomLCI.Host.

Por tanto:

- PdfPig **no se ejecuta in-process en el Host principal**;
- un proceso hijo nuevo procesa cada llamada;
- crash/stack overflow/OOM del parser sólo termina ese hijo;
- no se crea ProcessHandle público;
- no se registra en ResourceRegistry;
- se destruye inmediatamente al terminar la invocación.

## Cambio frente al diseño preliminar: no publicar un segundo runtime .NET

El diseño preliminar proponía un ejecutable self-contained separado `LoomLCI.PdfWorker.exe`.

Un probe temporal midió:

- Host self-contained actual: **110.740.092 bytes**;
- console worker mínimo + PdfPig self-contained: **86.102.218 bytes**;
- archivos realmente adicionales frente al runtime ya presente en Host: ~**5,93 MiB**, principalmente assemblies PdfPig.

Publicar un segundo self-contained completo duplicaría innecesariamente gran parte del runtime .NET.

### Decisión

Crear el proyecto privado:

`LoomLCI.PdfWorker`

pero como **class library interna**, referenciada sólo por `LoomLCI.Host`.

El proceso aislado será una segunda instancia del mismo ejecutable:

`LoomLCI.Host.exe --internal-pdf-worker-v1`

En ejecución framework-dependent de desarrollo/tests:

`dotnet LoomLCI.Host.dll --internal-pdf-worker-v1`

`Program.cs` detecta ese modo **antes** de crear el Generic Host/MCP y delega directamente a `LoomLCI.PdfWorker`.

Ventajas:

- aislamiento sigue siendo de proceso real;
- no se duplica el runtime self-contained;
- PdfPig sigue separado del Core/Windows/MCP;
- el publish normal de Host incorpora automáticamente el worker y sus dependencias;
- no hace falta localizar/deployar un segundo executable;
- el paquete aumenta aproximadamente por las dependencias PdfPig, no por otro runtime completo.

No ejecutar PdfPig desde el parent aunque la assembly esté presente en el payload.

### Resolución exacta del carrier Host

El último punto abierto sobre cómo relanzar el Host quedó verificado experimentalmente en Windows/.NET 10.

Ejecución framework-dependent mediante `dotnet App.dll`:

- `Environment.ProcessPath` -> `dotnet.exe`;
- `Assembly.GetEntryAssembly().Location` -> path absoluto de `App.dll`;
- `Environment.GetCommandLineArgs()[0]` -> path absoluto de `App.dll`.

Ejecución self-contained mediante `App.exe`:

- `Environment.ProcessPath` -> path absoluto de `App.exe`;
- `Assembly.GetEntryAssembly().Location` sigue apuntando al `.dll` del payload.

Por tanto el Host puede producir determinísticamente un descriptor de relanzamiento:

- si `Path.GetFileNameWithoutExtension(Environment.ProcessPath) == "dotnet"`:
  - executable = `Environment.ProcessPath`;
  - args prefix = `[Assembly.GetEntryAssembly().Location]`;
- en caso contrario:
  - executable = `Environment.ProcessPath`;
  - args prefix = `[]`;
- en ambos casos agregar `--internal-pdf-worker-v1` al final.

Esto cubre:

- dev/tests con `dotnet LoomLCI.Host.dll`;
- integration tests locales;
- integration tests contra Host publicado mediante `LOOMLCI_TEST_HOST_DLL`;
- runtime portable real iniciado como `LoomLCI.Host.exe`.

Para conservar layering limpio, **LoomLCI.Host debe resolver este descriptor y pasarlo/injectarlo al `PdfWorkerClient`/provider Windows**. `LoomLCI.Windows` no debe referenciar `LoomLCI.Host` ni descubrir por su cuenta qué entry point soporta el modo worker. Los tests Windows podrán inyectar un descriptor fake/controlado.

## Proceso hijo y Job Object

Reutilizar la infraestructura nativa existente, pero **sin pasar por ProcessCapability/ResourceRegistry**.

Actualmente:

`WindowsNativeProcessLauncher -> WindowsProcessResource -> WindowsJobObject`

ya garantiza creación del hijo dentro del Job mediante `PROC_THREAD_ATTRIBUTE_JOB_LIST`, evitando la carrera de crear primero y asignar después.

Microsoft documenta `PROC_THREAD_ATTRIBUTE_JOB_LIST` en Windows 10+; coincide con el mínimo actual de LoomLCI.

### Ajuste interno propuesto

Generalizar:

`WindowsJobObject.Create()`

a una variante interna con límite opcional de memoria de proceso.

Para el worker:

- `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`;
- `JOB_OBJECT_LIMIT_PROCESS_MEMORY`;
- `ProcessMemoryLimit = 256 MiB`.

El provider público de Process sigue llamando la variante sin memory cap y conserva exactamente su semántica actual.

### Semántica confirmada del límite de memoria

Microsoft documenta `JOB_OBJECT_LIMIT_PROCESS_MEMORY` como límite de memoria comprometida por proceso: cuando una nueva asignación intentaría superar el límite, **la asignación falla**; el Job Object no termina automáticamente el proceso por ese motivo.

Probe local con proceso .NET bajo Job Object real:

- límite 128 MiB: **12/12** ejecuciones alcanzaron `OutOfMemoryException`, lo capturaron y pudieron escribir una respuesta mínima antes de salir con code 0;
- límite objetivo 256 MiB: **3/3** ejecuciones hicieron lo mismo;
- no se observó terminación abrupta causada directamente por `JOB_OBJECT_LIMIT_PROCESS_MEMORY`.

Decisión de protocolo:

- preparar/prealocar antes del parseo una respuesta mínima `resource_limit` en bytes;
- capturar `OutOfMemoryException` en el borde superior del worker;
- escribir esa respuesta con el camino más simple posible y terminar normalmente;
- el parent devuelve `unsupported/pdf_resource_limit` **sólo si recibe explícitamente ese status válido**;
- si el worker no logra responder, termina non-zero o desaparece, clasificar como `execution_failed/pdf_worker_crashed`.

Así no se intenta inferir OOM a partir de exit codes ambiguos y se mantiene una degradación segura incluso si un estado extremo de memoria impide responder.

El worker no usa terminal/ConPTY: siempre **pipes**.

## Timeout

Timeout duro del worker: **20 s**.

No conviene usar solamente el timeout genérico de `InvocationRunner`, porque G1.2 necesita distinguir:

- cancelación del usuario/sesión;
- timeout específico del parser.

`PdfWorkerClient` debe poseer un CTS interno de 20 s enlazado al token de la invocación.

Si vence el timeout propio:

- terminar/disponer el Job;
- devolver:
  - `code = deadline_exceeded`
  - `details.reason = pdf_worker_timeout`.

Si se cancela el token externo, propagar `OperationCanceledException` para conservar la semántica normal de InvocationRunner.

## IPC

Usar un protocolo JSON one-shot sobre stdin/stdout.

No pasar paths por command line.

Flujo:

1. parent lanza Host child en modo worker;
2. parent escribe una única request JSON + newline en stdin;
3. worker procesa una sola request;
4. worker escribe una única response JSON + newline en stdout;
5. worker termina;
6. parent espera exit + drenaje completo de stdout/stderr;
7. valida tamaño/protocolo/status;
8. dispone inmediatamente el recurso/job.

El JSON serializado escapa newlines, por lo que cada frame permanece en una sola línea física.

### Límites internos sugeridos

- request: <= **1 MiB UTF-8**;
- response: <= **4 MiB UTF-8**;
- stderr diagnóstico leído por parent: <= **64 KiB**.

El límite público de 262.144 code points produce incluso en el peor caso de escapes Unicode un JSON claramente por debajo de 4 MiB.

El stdout no debe contener logs. Diagnóstico sólo por stderr.

## Espera de exit/output

La infraestructura Process actual observa el exit del root, pero los pumps de stdout/stderr pueden terminar instantes después.

Para evitar leer una response incompleta, agregar una primitiva **interna** de espera:

`WindowsProcessResource.WaitForExitAndOutputAsync(token)`

o equivalente, que espere:

1. exit del proceso;
2. EOF/drain de los pumps de pipes.

No exponerla como tool ni cambiar el lifecycle público de Process.

## Lectura estable del PDF

Aplicar la misma garantía fuerte usada por G1.1.

El parent abre el PDF con:

- `FileMode.Open`;
- `FileAccess.Read`;
- `FileShare.Read`.

Mantiene ese handle abierto **durante toda la ejecución del worker**.

Consecuencias:

- writers/delete/rename incompatibles quedan bloqueados mientras se procesa;
- si ya existe un writer incompatible, el open falla;
- el worker abre su propio `FileStream` también con `FileShare.Read` y se lo pasa a PdfPig;
- no hace falta comparar timestamps antes/después;
- no hace falta `file_changed_during_read` para G1.2.

Sharing violation:

- `code = busy`
- `retryable = true`
- `details.reason = file_busy`.

## Límites públicos

Mantener las decisiones existentes:

- PDF <= **64 MiB**;
- `startPage >= 1`;
- `maxPages = 1..25`;
- default `maxPages = 10`;
- páginas públicas 1-based;
- texto por página <= **65.536 Unicode code points**;
- texto agregado <= **262.144 Unicode code points**.

Contar con `Rune`/`EnumerateRunes()`, no con `string.Length`.

Una página que exceda 65.536 code points se trunca sin dividir un surrogate pair y reporta `textTruncated=true`.

Si agregar una nueva página superaría el máximo agregado, detener **antes** de esa página y devolver `nextPage`.

`PdfTextReadDto`:

- requestedPath
- fullPath
- sizeBytes
- pageCount
- startPage
- endPage
- totalTextLength
- outputLimitReached
- hasMoreAfter
- nextPage?
- pages[]

`PdfTextPageDto`:

- pageNumber
- text

- textTruncated

`textLength` y `totalTextLength` significan **Unicode code points**.

Un PDF sin capa textual es éxito con texto vacío; G1.2 no hace OCR.

Hasta que G1.3 exista, la descripción MCP no debe recomendar una tool todavía inexistente. Debe limitarse a advertir que scans/image-only pueden devolver poco o ningún texto.

## Estados del worker

El proceso puede responder semánticamente con exit code 0:

- `ok`;
- `password_protected`;
- `invalid_pdf`;
- `resource_limit`.

Mapeo parent:

- password_protected -> `unsupported/password_protected_pdf`;
- invalid_pdf -> `unsupported/invalid_pdf`;
- resource_limit -> `unsupported/pdf_resource_limit`, únicamente cuando el worker emitió explícitamente ese status válido.

`OutOfMemoryException` debe capturarse en el borde superior y responder usando el frame mínimo prealocado. Si esa respuesta no llega, el parent no debe asumir OOM: cae en `pdf_worker_crashed`.

Los fallos catchable ocurridos dentro del procesamiento PdfPig se consideran input PDF inválido/unsupported salvo:

- `PdfDocumentEncryptedException`;
- `OutOfMemoryException`;
- fallos de I/O/infrastructure claramente diferenciables.

No enviar stack traces al usuario. Tipo/mensaje acotado puede quedar sólo en stderr para diagnóstico.

Si el child:

- sale non-zero;
- muere por stack overflow;
- no produce response;
- produce JSON inválido/oversized;
- produce un status desconocido;

mapear a:

- `execution_failed`
- `details.reason = pdf_worker_crashed`.

## Arquitectura final G1.2

```text
ChatGPT / MCP
  -> VisualFilesTools.filesystem_read_pdf
      -> VisualFilesCapability.ReadPdfTextAsync
          -> WindowsVisualFilesProvider
              -> stable FileShare.Read handle
              -> PdfWorkerClient
                  -> WindowsNativeProcessLauncher (private use)
                      -> Job Object: kill-on-close + 256 MiB
                      -> LoomLCI.Host child --internal-pdf-worker-v1
                          -> LoomLCI.PdfWorker
                              -> PdfPig 0.1.16
                              -> ContentOrderTextExtractor
```

No ResourceRegistry ni ProcessHandle público.
