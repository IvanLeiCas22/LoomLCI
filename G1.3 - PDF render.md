# G1.3 - PDF render

> Estado: **implementado en `d25c3ce`; packaging/licencias cerrado en `63d256e`; validación Release, worker aislado, Host publicado, paquete portable, instalación y cutover completados.** El runtime final `0.1.0-dev-63d256e9b658` está healthy/ready. Sólo queda el smoke directo de `filesystem_render_pdf_page` desde un chat que refresque el catálogo de 21 a 22 tools; esta conversación conserva las acciones cargadas antes del upgrade.

## Objetivo

Agregar una única tool pública:

`filesystem_render_pdf_page(path, workId?, page, maxWidth=1800, maxHeight=2400)`

Debe renderizar exactamente una página PDF a PNG, preservando aspect ratio dentro de un bounding box, para documentos gráficos, tablas, diagramas y scans donde la extracción textual de G1.2 sea insuficiente.

G1.3 agrega **1 tool pública**:

- sin Work Plan: 19 -> **20**;
- Host normal con Work Plan: 21 -> **22**.

## Hallazgo que cambia el diseño preliminar

El diseño inicial de [[Bloque G - Visual Files]] proponía `Windows.Data.Pdf`.

El API funciona en un probe local `net10.0-windows10.0.19041.0`: un PDF real se cargó y produjo PNG válido 1200x848. Sin embargo, Microsoft lista explícitamente `Windows.Data.Pdf.PdfDocument`, `PdfPage`, `PdfPageDimensions` y `PdfPageRenderOptions` entre las WinRT APIs no soportadas en aplicaciones desktop sin el contexto requerido; las APIs que requieren package identity sólo están soportadas en desktop empaquetado con MSIX.

LoomLCI tiene como objetivo un runtime portable self-contained/unpackaged. Agregar MSIX o sparse package identity sólo para G1.3 introduciría instalación/registro y complejidad de deployment que contradicen el camino portable ya validado.

### Decisión

**No usar `Windows.Data.Pdf` como backend de G1.3.**

Usar:

- `bblanchon.PDFium.Win32 157.0.8086` como binario nativo PDFium;
- una capa P/Invoke mínima propia, no un wrapper genérico;
- `StbImageWriteSharp 1.16.7` para codificar PNG;
- ejecución dentro del proceso hijo privado ya usado conceptualmente por `LoomLCI.PdfWorker`.

La versión 157.0.8086 fue resuelta directamente contra NuGet durante esta investigación. `dotnet list package --vulnerable --include-transitive` no reportó vulnerabilidades conocidas y `--outdated` no encontró una versión posterior en los orígenes configurados.

## Alternativas evaluadas

### Windows.Data.Pdf

Ventaja: API mínima y sin dependencia redistribuida.

Problema decisivo: no es un backend oficialmente soportado para el modelo desktop portable/unpackaged de LoomLCI. Se descarta aunque el probe local funcione.

### MSIX / sparse package identity + Windows.Data.Pdf

Podría proporcionar el contexto requerido, pero cambia el modelo de distribución e instalación sólo para habilitar esta capability. No se justifica para G1.3.

### Interop nativo Windows PDF renderer

Existe `PdfCreateRenderer` / `IPdfRendererNative`, pero la ruta requiere COM/DirectX/DXGI y mantiene acoplamiento con la pila Windows PDF. Para una tool headless y portable aumenta mucho la complejidad frente a PDFium.

### PDFtoImage 5.4.0

Funcionó correctamente sobre PDFium + SkiaSharp:

- render real: 1200x848;
- PNG: 66.053 bytes;
- ~37 MiB peak working set en el probe.

Pero el publish de prueba arrastró aproximadamente 109 MiB, principalmente `libSkiaSharp.pdb` (~89 MiB), `libSkiaSharp.dll` (~12,3 MiB) y `pdfium.dll` (~7,2 MiB). No es una buena relación costo/beneficio para el paquete portable.

### PDFiumCore + StbImageWriteSharp

Funcionó y redujo el publish de prueba a ~7,8 MiB. Sin embargo, el wrapper `PDFiumCore` no conserva de forma fiable el native last-error de `FPDF_LoadDocument` en Windows: un PDF malformado produjo handle nulo, pero una llamada posterior a `FPDF_GetLastError()` devolvió 0.

La capa P/Invoke propia elimina esa ambigüedad capturando `Marshal.GetLastPInvokeError()` inmediatamente en la llamada marcada `SetLastError=true`.

## Evidencia local de la alternativa final

Con P/Invoke directo sobre `bblanchon.PDFium.Win32 157.0.8086` + `StbImageWriteSharp 1.16.7`:

- PDF vectorial real: render correcto;
- ruta Unicode `prueba áé ñ.pdf`: correcta;
- bounding 1200: salida 1200x848;
- bounding 4096x4096 sobre página A4 landscape: salida 4096x2896;
- PNG de ese máximo: 654.525 bytes;
- peak working set con encode directo desde el bitmap nativo: ~129 MiB;
- el mismo caso con copia intermedia del bitmap a `byte[]` subió a ~177 MiB, por lo que esa copia se descarta;
- PDF malformado: error nativo 3 = `FPDF_ERR_FORMAT`;
- PDF protegido generado temporalmente: error nativo 4 = `FPDF_ERR_PASSWORD`;
- publish de prueba con PDFium + encoder: ~7,7 MiB totales; el payload adicional relevante es ~7,5 MiB (`pdfium.dll` + encoder);
- un proyecto Host que referencia transitivamente al worker recibió automáticamente `pdfium.dll` y `StbImageWriteSharp.dll` en publish.

El render generado fue inspeccionado visualmente y mostró correctamente la lámina PDF usada como muestra.

## Aislamiento

Aunque PDFium es una biblioteca madura, sigue siendo un parser/renderizador nativo sobre input no confiable. No conviene cargarlo dentro de `LoomLCI.Host`.

Reutilizar el patrón de G1.2:

```text
LoomLCI.Host
  -> PdfWorkerClient / runner privado
      -> Job Object
          -> LoomLCI.Host child --internal-pdf-render-worker-v1
              -> LoomLCI.PdfWorker
                  -> PDFium native
                  -> StbImageWriteSharp
```

No crear un segundo executable self-contained ni un ProcessHandle público.

### Límites del worker

Decisión:

- timeout duro: **20 s**;
- process-memory cap: **256 MiB**;
- `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`;
- `FPDF_RENDER_LIMITEDIMAGECACHE`;
- one-shot: una request, una response, exit inmediato.

El render máximo medido quedó alrededor de 129 MiB de peak, por lo que 256 MiB deja margen razonable sin permitir crecimiento libre.

Como defensa adicional, inicializar PDFium con machine-time access deshabilitado mediante `FPDF_SetSandBoxPolicy`.

## Render

P/Invoke mínimo requerido:

- `FPDF_InitLibrary`;
- `FPDF_DestroyLibrary`;
- `FPDF_SetSandBoxPolicy`;
- `FPDF_LoadDocument`;
- `FPDF_CloseDocument`;
- `FPDF_GetPageCount`;
- `FPDF_LoadPage`;
- `FPDF_ClosePage`;
- `FPDF_GetPageWidth` / `FPDF_GetPageHeight`;
- `FPDFBitmap_CreateEx`;
- `FPDFBitmap_Destroy`;
- `FPDFBitmap_FillRect`;
- `FPDFBitmap_GetBuffer`;
- `FPDFBitmap_GetStride`;
- `FPDF_RenderPageBitmap`.

Render flags v0.1:

- annotations no interactivas: `FPDF_ANNOT`;
- RGBA transport para el encoder: `FPDF_REVERSE_BYTE_ORDER`;
- cache acotada: `FPDF_RENDER_LIMITEDIMAGECACHE`.

No inicializar FormFill/JavaScript/widgets en G1.3.

Fondo: blanco.

Encoder:

- `FPDFBitmap_CreateEx` con BGRA;
- codificar directamente desde el pointer nativo con `ImageWriter.WritePng(void*, ...)`;
- no crear una copia managed del bitmap;
- `LoomLCI.PdfWorker` requiere `AllowUnsafeBlocks=true`.

## Contrato público

Entrada:

```text
path
workId?
page
maxWidth = 1800
maxHeight = 2400
```

Reglas:

- `page` es 1-based y debe ser >=1;
- `maxWidth` y `maxHeight`: 256..4096;
- mantener aspect ratio dentro del bounding box;
- escalar tanto hacia abajo como hacia arriba;
- dimensiones finales = floor del tamaño escalado, mínimo 1;
- PDF máximo: **64 MiB**;
- una sola página por llamada;
- no aceptar password en G1;
- PNG máximo: **6 MiB**;
- `CallToolResult` visual público máximo: **9 MiB** mediante el estimator exacto ya implementado.

Resultado:

```text
PdfPageRenderDto
- requestedPath
- fullPath
- pdfSizeBytes
- page
- pageCount
- width
- height
- mimeType = image/png
- imageSizeBytes
```

Content MCP:

- TextContentBlock breve;
- `ImageContentBlock.FromBytes(png, "image/png")`.

Annotations MCP:

- ReadOnly = true;
- Destructive = false;
- Idempotent = true;
- OpenWorld = false.

## Lectura estable

Mantener la misma garantía que G1.2.

El parent abre el PDF con `FileShare.Read` y conserva ese handle durante toda la invocación del worker.

Así:

- un writer incompatible produce `busy/file_busy`;
- delete/rename incompatible queda bloqueado durante el render;
- el worker puede abrir el mismo path para lectura;
- no hace falta comparar timestamps antes/después.

El límite de 64 MiB se valida antes de lanzar el worker.

## IPC

Mantener protocolo JSON one-shot por stdin/stdout.

Request de render:

```text
fullPath
page
maxWidth
maxHeight
```

Response exitosa incluye metadata + PNG como `byte[]` JSON/base64.

Para el protocolo **interno** usar `JavaScriptEncoder.UnsafeRelaxedJsonEscaping`: el canal es local/controlado y evita que caracteres `+` del base64 se conviertan en `\u002B`, manteniendo una imagen de 6 MiB en ~8 MiB base64 más metadata.

Límites propuestos:

- response de render <= **9 MiB UTF-8**;
- stderr diagnóstico <= **64 KiB**;
- process spool existente de 64 MiB es suficiente.

El límite público MCP sigue usando el estimator exacto existente; no debe confundirse con el límite del protocolo interno.

## Estados y errores

No agregar códigos Loom top-level nuevos.

Mapeo:

| Caso | code | reason |
|---|---|---|
| input inválido | `invalid_argument` | específico cuando aporte |
| page fuera de rango | `invalid_argument` | `page_out_of_range` |
| archivo inexistente | `not_found` | - |
| ACL/OS denial | `access_denied` | - |
| writer/lock activo | `busy` | `file_busy` |
| PDF >64 MiB | `unsupported` | `pdf_too_large` |
| PDFium `FPDF_ERR_PASSWORD` | `unsupported` | `password_protected_pdf` |
| PDFium `FPDF_ERR_FORMAT` | `unsupported` | `invalid_pdf` |
| PDFium `FPDF_ERR_SECURITY` | `unsupported` | `unsupported_pdf_security` |
| PNG >6 MiB o MCP >9 MiB | `unsupported` | `rendered_image_too_large` |
| worker OOM controlado | `unsupported` | `pdf_render_resource_limit` |
| timeout 20 s | `deadline_exceeded` | `pdf_render_worker_timeout` |
| crash/no response/protocolo inválido | `execution_failed` | `pdf_render_worker_crashed` |
| fallo de render clasificable sólo como infraestructura | `execution_failed` | `pdf_render_failed` |

`rendered_image_too_large` debe indicar que se reintente con `maxWidth`/`maxHeight` menores.

## Arquitectura final G1.3

```text
ChatGPT / MCP
  -> VisualFilesTools.filesystem_render_pdf_page
      -> VisualFilesCapability.RenderPdfPageAsync
          -> WindowsVisualFilesProvider
              -> stable FileShare.Read handle
              -> PdfWorkerClient / private runner
                  -> WindowsNativeProcessLauncher
                      -> Job Object 256 MiB + kill-on-close
                      -> LoomLCI.Host child --internal-pdf-render-worker-v1
                          -> LoomLCI.PdfWorker
                              -> PDFium native
                              -> StbImageWriteSharp -> PNG
      -> McpVisualPayloadLimits
      -> ImageContentBlock.FromBytes
```

Core sigue sin dependencias nativas/Windows. Las dependencias PDFium/encoder deben vivir en `LoomLCI.PdfWorker`.

Conviene generalizar internamente el launch/wait/drain/timeout de `PdfWorkerClient` para compartirlo entre text y render sin alterar el protocolo G1.2.

## Packaging

El probe de transitividad confirmó que el Host publicado recibe automáticamente los runtime assets nativos del worker.
